## 1. 개요

숨비투어의 세 번째 업무 기능이다. 관리자는 Payload 관리자 화면에서 신청 상태를 바꾸고, 신청자가 요청 사항에 적은 민감정보를 지우고, 회차별 참가자 목록을 CSV로 받고, 첫 화면에서 다가오는 회차의 신청 현황을 본다. 이 모든 작업은 별도 기록으로 남는다. 범위는 다음 여섯 가지다.

1. 신청 상태 변경: 상세 화면에서 `status`만 편집(대기·확정·취소 자유 전환), 다른 필드는 읽기 전용, 일괄 변경 없음
2. 상태 변경 규칙: 취소 복원 시 정원 확인(사이트 접수와 동시에 일어나도 안전), 취소로 마감이 풀리지 않음, 취소일 기록
3. 요청 사항 삭제: 상세 화면의 삭제 동작 하나로만 요청 사항 글 전체를 지우고 지운 시각을 남김
4. 회차별 참가자 CSV: 관리자 전용, 엑셀에서 한글이 깨지지 않음, 수식 주입 차단, URL·파일 이름에 개인정보 없음, 캐시 금지
5. 회차 현황 대시보드: 관리자 첫 화면의 표 하나(차트 없음), 점유 인원 단일 정의, 회차 수와 무관한 질의 수, 행마다 CSV 링크
6. 관리자 작업 기록: 상태 변경·요청 사항 삭제·CSV 내려받기를 신청자 개인정보 없이 덧붙이기 전용 컬렉션에 기록

### 2.2 사용자가 확정한 사항 (2026-11-12 인터뷰, 구속력 있음)

- **D1. 상태 변경 위치**: 관리자 신청 상세에서만. `status`만 편집할 수 있고(대기·확정·취소 자유 전환) 다른 필드는 모두 읽기 전용이다. 일괄 작업은 없다.
- **D2. 기존 제품 규칙**: 취소 복원이 정원을 넘으면 막는다. 신청을 취소해도 마감된 회차는 자동으로 다시 열리지 않는다. 복원 확인은 사이트 접수와 같은 회차 행 잠금 규칙으로 동시성에 안전해야 한다. `cancelledAt` 처리는 초안 작성자가 정해 기록한다.
- **D3. 민감정보 삭제**: 상세 화면의 "요청 사항 삭제" 동작이 요청 사항 글 전체를 지우고 지운 시각을 기록한다. 그 밖에는 관리자가 요청 사항을 고칠 수 없다.
- **D4. CSV**: 회차별 참가자 목록(접수번호·이름·연락처·이메일·인원·상태·요청 사항), 관리자 전용, UTF-8 BOM, 수식 주입 방지, 파일 이름·URL에 개인정보 없음, 캐시 금지.
- **D5. 대시보드**: 관리자 첫 화면의 다가오는 회차 표(투어 이름·시작 일시·정원·대기 인원·확정 인원·남은 자리·회차 상태), 단일 점유 인원 정의, N+1 없음, 행마다 CSV 링크, 차트 없음.
- **D6. 작업 기록**: 누가(관리자 ID)·무엇을·언제 — 상태 변경(이전→이후), 요청 사항 삭제, CSV 내려받기(회차). 신청자 개인정보 없는 별도 덧붙이기 전용 컬렉션, 관리자는 읽기만, API로는 누구도 만들거나 고치거나 지울 수 없다.
- **D7. 제외**: 이메일 알림, 일괄 상태 변경, 차트, 회원, 배포, SPEC-APPLY-001 지적 F1·F2.
- **추가 확인 (2026-11-16, `interview.md` "추가 확인")**: 취소 복원으로 정원이 꽉 차면 회차를 자동 마감한다. 회차별 CSV에 취소 신청을 넣고 상태 열로 구분한다. 대시보드에는 비공개 투어의 회차도 보이며 `비공개`로 표시한다. 관리자 작업 기록은 2년 보관한다(가정 A6).

Tier는 M으로 정한다. 신청 운영이라는 한 도메인이고 프로젝트 원칙을 바꾸지 않는다. 제품 코드는 약 700~900줄, 테스트는 그보다 조금 많을 것으로 보이고 새 파일과 수정 파일을 합치면 Tier M 지침(5~15개 파일)을 넘을 수 있다. SPEC-APPLY-001도 같은 규모에서 M을 유지했다. 요구사항 16개·수용 기준 16개로 Tier M 예산 안이며, 넘칠 때의 분할 기준은 `plan.md` §A.3에 둔다.

### 2.3 이 SPEC이 내리는 결정 (요약 — 근거는 `plan.md` §B)

- **편집 범위는 Payload 접근 규칙으로**: `applications`의 컬렉션 수정 권한을 "관리자 + 문서 한 건"으로 열고, `status`를 뺀 모든 필드에 필드 단위 수정 거부를 건다. Payload는 수정이 거부된 필드 값을 오류 없이 버리고 저장된 값을 유지하며, 관리자 화면은 그 필드를 읽기 전용으로 그린다(`plan.md` §A.2). 일괄 수정은 `disableBulkEdit`로 API와 화면 모두에서 막는다.
- **모든 신청 수정은 한 가지 순서로 잠근 뒤 판단**: 상태 변경 요청이든 요청 사항 삭제든 그 밖의 수정이든 `applications`의 모든 수정은 같은 트랜잭션에서 회차 행 → 신청 행 순서로 잠근 뒤 현재 값과 점유 인원을 다시 읽고, 그 값으로 판단하고 저장한다. Payload는 들어오지 않은 필드를 잠금 전에 읽은 문서 값으로 채워 넘기므로(`plan.md` §A.2), 상태 변경 요청인지는 필드 처리 전의 원본 입력으로 가린다. 사이트 접수와 같은 회차 행을 잠그므로 둘은 회차마다 한 줄로 서고, 잠금 순서가 하나라 요청 사항 삭제와 상태 변경 사이에 교착이 생기지 않는다.
- **복원으로 정원이 꽉 차면 마감**: 사이트 접수의 자동 마감과 같은 규칙이다. 취소는 회차 상태를 건드리지 않는다.
- **요청 사항 삭제와 CSV는 관리자 전용 사용자 지정 API**: Payload 컬렉션 엔드포인트로 두고 처리 함수 안에서 관리자인지 직접 확인한다(엔드포인트에는 접근 규칙이 자동 적용되지 않음, `plan.md` §A.2). 핵심 로직은 `src/lib/`에 둬 통합 테스트가 Next 없이 실제 DB로 검증한다.
- **작업 기록은 같은 트랜잭션에서**: 상태 변경·요청 사항 삭제는 작업과 기록이 함께 커밋되거나 함께 되돌려진다. CSV는 기록을 먼저 남기고, 기록에 실패하면 파일을 주지 않는다.
- **새 npm 패키지 없음**: CSV는 직접 만든다(필드 수 7개, 규칙이 단순함). 관리자 화면 구성 요소는 이미 설치된 `@payloadcms/ui`만 쓴다.

### 2.4 기록된 가정

- **A1. 관리자 판정**: SPEC-TOUR-001 가정 A1과 같다(`users` 컬렉션 사용자, `src/lib/access.ts` `isAdmin`).
- **A2. 관리자는 한 명이다**(`product.md` §3). 그래도 같은 관리자가 두 탭에서 저장하거나 사이트 접수와 동시에 저장하는 경우가 있으므로 동시성 규칙은 그대로 둔다.
- **A3. 취소일과 보관 기준일**: 보관 기준일은 SPEC-APPLY-001 가정 A6 그대로 "`cancelledAt`이 있으면 그 날, 없으면 회차 종료 일시"다. 취소에서 되돌린 신청은 다시 유효한 신청이므로 `cancelledAt`을 비워 기준일을 회차 종료 일시로 돌린다. 취소했던 이력은 작업 기록에 남는다. 다시 취소하면 그때의 시각이 새 기준일이 된다.
- **A4. 접수 번호는 신청자 개인정보가 아니다**: 무작위 공개 식별자이며 접수 완료 화면에서 보이는 정보도 투어·회차·인원·상태뿐이다(SPEC-APPLY-001 가정 A8). 작업 기록은 읽기 쉽도록 접수 번호를 담는다.
- **A5. 관리자 화면 언어**: Payload 관리자 화면 기본 문구는 영어이고, 이 SPEC이 더하는 표·버튼·라벨은 한국어다. 관리자에게 보이는 오류 문구는 `error_messages: en`에 따라 영문 고정 문구다.
- **A6. 작업 기록 보관 기간**: 사용자 결정(2026-11-16)으로 **2년**이다. 기록에 생성 일시를 남겨 보관 기준일로 쓴다. 2년이 지난 기록의 자동 삭제는 이 SPEC 범위 밖이며 배포 단계에서 정기 작업으로 만든다. 개인정보 처리 시스템 접속 기록의 법정 보관 기간(안전성 확보조치 기준)과 맞는지는 출시 전 변호사 확인 목록으로 넘긴다(`plan.md` §G R20).
- **A7. 버전 기록이 없다**: `applications`는 Payload 버전(`versions`)을 켜지 않았다. 켜면 지운 요청 사항이 이전 버전에 남으므로, 켜는 SPEC은 이 SPEC의 삭제 요구를 다시 검토해야 한다.

### 2.5 용어

- **상태 변경 요청**: 수정 요청의 원본 데이터(Payload가 필드를 처리하기 전, 요청 본문·로컬 API `data`에 들어온 그대로의 객체)에 `status` 키가 있는 `applications` 수정. 관리자 화면 저장은 상태 입력란을 함께 보내므로 상태 변경 요청이다. Payload가 저장 직전에 채워 넣은 `status`는 판별에 쓰지 않는다.
- **상태 변경**: 상태 변경 요청 중 요청한 값이 잠금 뒤 다시 읽은 현재 상태와 다른 것. 값이 같으면 상태 변경이 아니다.
- **잠긴 필드**: `applications`에서 `status`를 뺀 모든 필드. 접근 규칙을 적용하는 경로로는 바꿀 수 없고, 서버 코드만 정해진 동작(취소일 처리, 요청 사항 삭제)으로 바꾼다.
- **회차 없는 신청**: 회차 관계가 비어 있는 신청(SPEC-APPLY-001 지적 F1의 `ON DELETE SET NULL` 결과로만 생김). `session` 필드가 필수라 Payload 필드 검증이 그 신청의 어떤 저장도 받지 않으므로, 이 SPEC은 그 신청의 모든 수정을 먼저 거부한다(REQ-ADMIN-005, `plan.md` §A.2).
- **비공개 투어**: `tours`의 `published`가 거짓인 투어.
- **취소 복원**: 상태를 취소(`cancelled`)에서 대기(`pending`) 또는 확정(`confirmed`)으로 바꾸는 상태 변경.
- **점유 인원·남은 자리**: SPEC-APPLY-001 정의 그대로(대기·확정 신청 인원의 합계, 정원 − 점유 인원이며 0 미만이면 0).
- **회차 행 잠금**: `tour_sessions`의 그 회차 행에 트랜잭션 안에서 거는 `SELECT … FOR UPDATE`. SPEC-APPLY-001 정원 확인 구간과 같은 잠금이다.
- **요청 사항 삭제**: 신청 하나의 요청 사항 글 전체를 비우고 삭제 시각(`requestsDeletedAt`)을 기록하는 관리자 동작.
- **참가자 CSV**: 회차 하나의 모든 신청을 한 행씩 담은 CSV 파일.
- **회차 현황 대시보드**: 관리자 첫 화면(`/admin`)에 그리는 다가오는 회차 표.
- **다가오는 회차**: 시작 일시가 현재보다 뒤인 회차.
- **작업 기록**: `admin-audit-logs` 문서 하나. 작업 종류, 관리자 ID, 시각, 대상(신청 ID·접수 번호·회차 ID), 상태 변경의 이전·이후 값, CSV 행 수를 담는다.
- **접근 규칙을 적용하는 경로**: REST, GraphQL, `overrideAccess: false`인 로컬 API, 관리자 화면.
- **개인정보**: 신청자의 이름·이메일·연락처·요청 사항(SPEC-APPLY-001과 같음).
- **테스트 데이터 표식**: SPEC-TOUR-001·SPEC-APPLY-001과 같다. 테스트 관리자는 `@example.test` 이메일을 쓴다.

## 3. 요구사항 (GEARS)

패턴 표기: [Ubiquitous] 상시 / [Event-driven] **When** / [State-driven] **While** / [Unwanted] 금지. Tier M 예산(요구사항 16개 이하)에 맞춰 관련 조항을 묶었다.

### 3.1 데이터 모델과 접근 규칙

- **REQ-ADMIN-001** [Ubiquitous] Payload 설정에 등록된 컬렉션 중 시스템 컬렉션(slug가 `payload-`로 시작)을 뺀 목록은 정확히 `users`, `media`, `tours`, `tour-sessions`, `applications`, `application-attempts`, `admin-audit-logs`여야 한다. 이 요구사항은 SPEC-APPLY-001 REQ-APPLY-002의 목록을 대체한다.
- **REQ-ADMIN-002** [State-driven + Unwanted] **While** 요청이 관리자의 것이고 신청 한 건을 ID로 지정하면, 접근 규칙을 적용하는 경로는 그 신청의 수정을 받아야 하며, 그 수정이 바꿀 수 있는 필드는 `status` 하나여야 한다. 접근 규칙을 적용하는 어떤 경로로도 `status` 외 필드(회차, 이름, 이메일, 연락처, 인원, 요청 사항, 접수 번호, 동의 기록, 취소일, 요청 사항 삭제 일시)의 저장값은 바뀌지 않아야 한다. 신청 한 건을 지정하지 않은 수정(일괄 수정)은 관리자를 포함한 모두에게 HTTP 403으로 거부되어야 한다. 관리자가 아닌 요청의 수정, 그리고 모든 요청의 생성·삭제는 SPEC-APPLY-001과 같이 거부되어야 한다. 이 요구사항은 SPEC-APPLY-001 REQ-APPLY-003의 `applications` "수정은 관리자도 거부" 부분만 대체하며, 나머지 조항(`application-attempts` 규칙, 읽기 규칙, 생성 경로)은 그대로다.
- **REQ-ADMIN-003** [Event-driven] **When** 관리자가 관리자 화면에서 신청 상세를 열면, 관리자 화면은 상태를 대기·확정·취소 중에서 고르는 편집 가능한 입력란과 저장 버튼을 보여야 하고, 그 밖의 신청 필드는 편집할 수 없게 보여야 한다. 신청 목록에는 "새로 만들기"와 여러 건을 고른 뒤의 일괄 편집·일괄 삭제 동작이 없어야 한다.

### 3.2 상태 변경 규칙

- **REQ-ADMIN-004** [Event-driven] **When** 상태 변경이 저장되면, 시스템은 새 상태를 저장해야 한다. 새 상태가 취소이면 `cancelledAt`을 그 처리 시각으로, 이전 상태(잠금 뒤 다시 읽은 현재 상태)가 취소이고 새 상태가 대기·확정이면 `cancelledAt`을 비워야 하며, 대기와 확정 사이의 변경은 `cancelledAt`을 바꾸지 않아야 한다. **When** 상태 변경 요청의 값이 잠금 뒤 다시 읽은 현재 상태와 같으면, 시스템은 상태와 `cancelledAt`을 잠금 뒤 읽은 값 그대로 저장하고 작업 기록을 남기지 않아야 한다.
- **REQ-ADMIN-005** [Event-driven + Unwanted] **When** 취소 복원이 요청되면, 시스템은 회차 행 잠금 뒤 읽은 그 회차의 점유 인원에 복원할 신청의 인원을 더한 값을 정원과 비교해야 한다. **When** 그 값이 정원을 넘으면, 시스템은 변경을 거부하고 영문 고정 문구 `RESTORE_CAPACITY_EXCEEDED: …`(HTTP 409, `acceptance.md` §0)로 끝나야 하며 신청·회차·작업 기록 어느 것도 바꾸지 않아야 한다. **When** 그 값이 정원과 같고 회차가 모집 중이면, 시스템은 같은 트랜잭션에서 회차를 마감으로 바꿔야 한다. 이미 마감된 회차에 자리가 남아 있으면 복원은 받아들이고 회차는 마감 상태 그대로 두어야 한다. **When** 회차 없는 신청의 수정이 요청되면(취소 복원, 그 밖의 상태 변경, 같은 상태 저장, 상태 없는 수정, 요청 사항 삭제 모두), 시스템은 그 수정을 거부하고 영문 고정 문구 `SESSION_MISSING: …`(HTTP 409)로 끝나야 하며 신청·회차·작업 기록 어느 것도 바꾸지 않아야 한다.
- **REQ-ADMIN-006** [Ubiquitous + Event-driven + Unwanted] 상태 변경 요청과 요청 사항 삭제를 포함한 `applications`의 모든 수정은 하나의 트랜잭션 안에서 그 신청의 회차 행을 먼저, 이어서 그 신청 행을 잠가야 하며(회차 없는 신청의 수정은 잠그기 전에 REQ-ADMIN-005에 따라 거부), 잠근 뒤의 별도 문장으로 읽은 현재 상태·인원·요청 사항·요청 사항 삭제 일시·취소일과 점유 인원으로만 판단해야 한다. 그 수정이 정해진 규칙으로 바꾸는 필드 외의 잠긴 필드와, 상태 변경 요청이 아닌 수정의 `status`는 잠근 뒤 읽은 값으로 저장해야 한다. 시스템은 잠금 전에 읽어 둔 문서 값으로 판단하거나 그 값을 저장하지 않아야 한다. 사이트 접수(SPEC-APPLY-001 서버 제출 경로)와 상태 변경이 같은 회차에 동시에 일어나도 커밋된 점유 인원은 그 둘 때문에 정원을 넘지 않아야 하며, 요청 사항 삭제와 상태 변경이 같은 신청에 동시에 일어나도 둘 다 교착 없이 끝나고 두 결과가 모두 남아야 한다. **When** 회차 행이나 신청 행의 잠금을 5초 안에 얻지 못하면, 시스템은 아무것도 바꾸지 않고 영문 고정 문구 `SESSION_BUSY: …`(HTTP 409)로 끝나야 한다.
- **REQ-ADMIN-007** [State-driven + Unwanted] **While** 회차가 마감 상태이면, 그 회차 신청의 취소는 회차 상태를 바꾸지 않아야 하며, 시스템은 마감된 회차를 스스로 다시 열지 않아야 한다(SPEC-APPLY-001 REQ-APPLY-010과 같은 규칙을 관리자 경로에도 적용).

### 3.3 요청 사항 삭제

- **REQ-ADMIN-008** [Event-driven + State-driven + Unwanted] **While** 신청의 요청 사항이 비어 있지 않으면, 관리자 신청 상세는 "요청 사항 삭제" 동작을 확인 단계와 함께 보여야 한다. **When** 관리자가 삭제를 확인하면, 서버는 하나의 트랜잭션 안에서(잠금 순서는 REQ-ADMIN-006) 그 신청의 요청 사항 글 전체를 비우고 `requestsDeletedAt`을 처리 시각으로 기록하고 작업 기록을 남겨야 하며, 상태·`requestsConsentAt`과 다른 필드는 바꾸지 않아야 한다. 요청 사항이 비어 있는지는 잠근 뒤 읽은 값으로 판단한다. **When** 그 값이 이미 비어 있으면 `REQUESTS_EMPTY`(HTTP 409)로, 요청이 관리자의 것이 아니면 `FORBIDDEN`(HTTP 403)으로, 신청 식별 값이 1~2147483647 정수가 아니거나 신청이 없으면 `NOT_FOUND`(HTTP 404)로, 회차 행이나 신청 행의 잠금을 5초 안에 얻지 못하면 `SESSION_BUSY`(HTTP 409)로, 회차 없는 신청이면 `SESSION_MISSING`(HTTP 409, REQ-ADMIN-005)으로, 그 밖의 처리 오류이면 `INTERNAL_ERROR`(HTTP 500)로 끝나야 하며, 어느 경우든 아무것도 바꾸지 않아야 한다. 요청 사항 삭제가 커밋된 뒤에는 어떤 수정도(삭제 전에 읽힌 문서로 진행된 같은 상태 저장 포함) 지운 글을 다시 저장하거나 `requestsDeletedAt`을 비우지 않아야 한다. 이 동작 말고는 관리자가 요청 사항 글을 바꿀 수 없어야 한다.

### 3.4 참가자 CSV

- **REQ-ADMIN-009** [Event-driven] **When** 관리자가 회차 하나의 참가자 CSV를 요청하면, 서버는 그 회차에 속한 모든 신청(대기·확정·취소)을 신청 시각 순으로 한 행씩 담은 CSV를 돌려주어야 한다. 첫 행은 `접수번호`, `이름`, `연락처`, `이메일`, `인원`, `상태`, `요청 사항` 순의 머리글이고, 상태는 `대기`·`확정`·`취소`로 적어야 한다. 파일은 UTF-8 BOM으로 시작하고, 줄 끝은 CRLF이며, 모든 칸을 큰따옴표로 감싸고 칸 안의 큰따옴표는 두 번 써야 한다.
- **REQ-ADMIN-010** [Unwanted + Event-driven] CSV의 어떤 칸도 첫 글자가 `=`, `+`, `-`, `@`, 탭, CR인 채로 나가지 않아야 하며, 그런 칸은 앞에 `'`를 붙여야 한다. CSV 요청의 URL 경로와 파일 이름은 회차 ID 외의 값을 담지 않아야 하고, 응답은 첨부 파일(`Content-Disposition: attachment`)이면서 `Cache-Control`에 `no-store`를 담아야 한다. **When** 요청이 관리자의 것이 아니거나 `Sec-Fetch-Site`가 `cross-site`이면, 서버는 CSV 없이 `FORBIDDEN`(HTTP 403)으로, 회차 식별 값이 1~2147483647 정수가 아니거나 회차가 없으면 `NOT_FOUND`(HTTP 404)로 끝나야 한다.

### 3.5 회차 현황 대시보드

- **REQ-ADMIN-011** [Event-driven] **When** 관리자가 관리자 첫 화면을 열면, 관리자 화면은 다가오는 회차를 시작 일시 순으로 한 행씩 담은 표를 보여야 한다. 열은 투어 이름, 시작 일시(서울 시각), 정원, 대기 인원, 확정 인원, 남은 자리, 회차 상태(`모집 중`·`마감`)이고, 행마다 그 회차의 참가자 CSV 링크가 있어야 한다. 다가오는 회차는 투어의 공개 여부와 관계없이 모두 담아야 하며, 비공개 투어의 행은 투어 이름 칸에 `비공개` 표시를 함께 보여야 하고 공개 투어의 행에는 그 표시가 없어야 한다. 대기 인원과 확정 인원은 각 상태 신청 인원의 합계이고, 그 둘의 합은 SPEC-APPLY-001 점유 인원 정의와 같아야 하며, 남은 자리는 SPEC-TOUR-001의 단일 계산 지점에 그 점유 인원을 넘겨 구해야 한다. 차트는 두지 않는다.
- **REQ-ADMIN-012** [Ubiquitous] 대시보드 데이터를 한 번 구할 때 데이터베이스에 보내는 질의 수는 다가오는 회차 수에 따라 늘지 않아야 하며, 그 질의는 모두 트랜잭션 밖 연결 풀로 나가야 한다.

### 3.6 작업 기록

- **REQ-ADMIN-013** [Event-driven] **When** 상태 변경이 커밋되거나, 요청 사항 삭제가 커밋되거나, 참가자 CSV를 돌려주면, 시스템은 작업 종류, 작업한 관리자 ID(사람이 아닌 서버 경로는 비움), 처리 시각, 대상(신청 ID·접수 번호·회차 ID 중 해당하는 것), 상태 변경의 이전·이후 상태, CSV의 행 수를 담은 작업 기록을 남겨야 한다. 상태 변경과 요청 사항 삭제의 기록은 그 작업과 같은 트랜잭션에서 저장되어야 하며, 기록이 실패하면 작업도 되돌려져야 한다. CSV 기록은 응답 전에 저장되어야 하고, 실패하면 서버는 CSV 없이 `INTERNAL_ERROR`(HTTP 500)로 끝나야 한다. 거부된 요청(403·404·409)은 기록하지 않는다.
- **REQ-ADMIN-014** [Unwanted + State-driven] `admin-audit-logs`의 생성·수정·삭제는 접근 규칙을 적용하는 모든 경로에서 익명 방문자와 관리자 모두에게 거부되어야 한다. **While** 요청이 관리자의 것이 아니면, 작업 기록 읽기 결과는 비어 있거나 권한 오류여야 한다. 관리자는 관리자 화면에서 작업 기록 목록과 상세를 편집할 수 없는 상태로 읽을 수 있어야 한다. 작업 기록은 신청자 개인정보를 담는 필드를 갖지 않아야 한다.

### 3.7 개인정보와 테스트

- **REQ-ADMIN-015** [Unwanted] 상태 변경·요청 사항 삭제·CSV·대시보드 경로에서 이 SPEC의 코드(훅, `src/lib/` 처리 함수, 엔드포인트, 관리자 화면 구성 요소)는 신청자 개인정보를 서버 로그, 오류 코드, 오류 문구(API 응답과 관리자 화면 알림), URL(경로와 질의 문자열), CSV 파일 이름, 작업 기록에 담지 않아야 한다. 이 SPEC의 코드가 남기는 로그는 오류 코드, 오류 종류 이름, 신청·회차 ID만 담아야 하고, 이 SPEC의 코드가 던지는 오류는 원인 오류(`cause`)나 원시 오류 문구를 담지 않아야 한다. 신청자 개인정보는 CSV 본문과 관리자 신청 상세에서만 관리자에게 보인다. Payload가 저장 단계의 데이터베이스 오류를 이 SPEC 코드 밖에서 스스로 기록하는 동작은 이 요구사항의 범위가 아니며 잔여 위험과 출시 전 점검 항목으로 관리한다(`plan.md` §B.8·§G R23).
- **REQ-ADMIN-016** [Ubiquitous] 테스트 실행(`pnpm test`, `pnpm e2e`)은 이 SPEC의 순수 함수(단위), 상태 변경 규칙·필드 편집 범위·요청 사항 삭제·CSV·대시보드 데이터·작업 기록·접근 규칙(통합, 실제 PostgreSQL), 사이트 접수와 취소 복원을 실제 DB에서 동시에 실행해 정원을 넘지 않음을 확인하는 동시성 테스트와, 요청 사항 삭제와 다른 수정을 같은 신청에 동시에 실행해 교착 없이 두 결과가 모두 남고 지운 요청 사항이 되살아나지 않음을 확인하는 동시성 테스트(통합), 관리자 화면 상태 변경·요청 사항 삭제·대시보드·CSV 내려받기와 API 권한(E2E, 테스트 관리자로 로그인)을 검증해야 한다. 테스트는 실제 관리자 계정을 쓰거나 바꾸지 않고, 필요한 관리자 계정·투어·회차·신청·작업 기록을 테스트 데이터 표식을 붙여 스스로 만들고 끝나면 지워야 한다. `src/lib/` 합산 라인 커버리지 85% 기준과 기존 품질 게이트(타입·빌드·린트·포맷·잠금 파일 불변)는 계속 통과해야 한다.

## 4. 비기능 제약

- **보안**: 사용자 지정 엔드포인트는 Payload 접근 규칙이 자동으로 걸리지 않으므로 처리 함수가 관리자 여부를 직접 확인한다. 상태를 바꾸는 엔드포인트는 POST만 받는다. 관리자 쿠키 인증의 출처 검사는 Payload 기본 동작(`csrf` 허용 목록과 `Sec-Fetch-Site`)을 따른다(`plan.md` §A.2).
- **개인정보**: 작업 기록에는 신청자 개인정보 필드가 없다. 요청 사항 삭제는 되돌릴 수 없고, 지운 글은 DB와 화면 어디에도 남지 않는다(가정 A7 — 버전 기록 없음).
- **동시성**: 데이터베이스 기본 격리 수준(Read Committed)을 바꾸지 않는다. `applications`의 모든 수정(상태 변경 요청, 요청 사항 삭제, 그 밖의 수정)은 회차 행 → 신청 행 한 가지 순서로 잠근다. 사이트 접수는 회차 행만 잠그고 새 신청을 넣는다. 어느 경로도 신청 행을 쥔 채 회차 행을 기다리지 않으므로 `applications` 행과 `tour_sessions` 행 사이에는 순환 대기가 없다. 복원으로 회차를 마감할 때는 이미 쥔 회차 행을 같은 트랜잭션 연결의 원시 SQL로 고쳐, 행 잠금을 쥔 뒤 Payload 문서 잠금 테이블(`payload-locked-documents`)을 건드리지 않는다. Payload가 모든 단건 수정의 시작(행 잠금을 쥐기 전)에 그 문서의 문서 잠금 행을 지우는 단계는 5초 제한 밖에서 기다릴 수 있으며, 그 대기와 이 SPEC 범위 밖 경로(사이트 접수의 자동 마감)의 교착 가능성은 잔여 위험으로 관리한다(`plan.md` §B.2·§G R26). 잠금 구간 안의 질의는 모두 같은 트랜잭션 연결을 쓴다.
- **접근성**: 대시보드 표는 `<table>`·`<th scope>`로 머리글을 연결하고, 삭제 버튼과 CSV 링크는 이름이 있는 컨트롤이다.
- **Windows 호환**: 새 검증 명령은 PowerShell 5.1에서 동작해야 한다.
- **비용**: 새 유료 서비스·외부 저장소·새 npm 패키지를 쓰지 않는다.

수용 기준과 검증 명령은 `acceptance.md`에 둔다.

## 5. 제외 범위 (Out of Scope)

### Out of Scope — 일괄 작업과 차트

- 여러 신청의 상태를 한 번에 바꾸는 일괄 변경(목록 선택 후 편집 포함)
- 대시보드의 차트·그래프, 기간별 통계, 투어별 합계
- 여러 회차를 한 파일로 받는 CSV, 엑셀(`.xlsx`) 형식

### Out of Scope — 알림·회원·배포 (다른 로드맵)

- 상태 변경 시 신청자에게 보내는 이메일, 새 신청 관리자 알림(로드맵 5번)
- 회원 인증과 회원 신청, 내 신청 내역(로드맵 4번)
- 운영 배포 설정, 서버리스 함수 시간·응답 크기 제한 확인(로드맵 8번)

### Out of Scope — SPEC-APPLY-001에서 미룬 지적 (사용자 결정 "나중에")

- F1: `TourSessions.ts` 회차 삭제 거부 검사와 첫 신청 커밋 사이의 경합(외래 키가 `ON DELETE SET NULL`이라 그 사이 삭제되면 신청의 회차가 비는 문제). 이 SPEC은 그렇게 생긴 회차 없는 신청의 모든 수정을 `SESSION_MISSING`으로 거부만 하며, 그 신청의 요청 사항(민감정보) 삭제는 F1 해결 때 다룬다
- (사용자 결정 대상이 아닌 기록 항목 — plan-audit 2회차가 찾은 기존 경로) SPEC-APPLY-001 사이트 접수의 자동 마감(`submit-application.ts`의 중첩 `payload.update(tour-sessions)`)이 회차 행을 쥔 채 문서 잠금 행을 지우는 순서(관리자 화면의 회차 저장과 교착 가능, `plan.md` §G R26). `submit-application.ts`는 이 SPEC에서 바꾸지 않는다
- F2: `submit-application.ts` 잠금 구간 안 `create`·`update`의 `depth: 0` 지정

### Out of Scope — Payload 기본 오류 기록

- Payload가 REST·관리자 화면 저장 실패 때 이 SPEC 코드 밖에서 남기는 오류 기록(데이터베이스 오류 문구에 질의 바인딩 값이 실릴 수 있음)의 정리·가림. 운영 로깅 설정은 배포 단계(로드맵 8번)의 출시 전 점검 항목으로 넘긴다(`plan.md` §G R23)

### Out of Scope — 데이터 관리

- 회차 정원을 점유 인원보다 작게 바꾸는 경우의 처리, 관리자의 회차 마감 해제 화면 추가 작업(기존 회차 상태 필드 수정은 그대로)
- 요청 사항 외 신청 필드(이름·연락처 등)의 수정·정정 기능
- 보유기간이 지난 신청·요청 사항의 자동 파기, 2년이 지난 작업 기록의 자동 파기(가정 A6)
- 작업 기록의 검색·필터 화면 추가 작업, 작업 기록 내보내기

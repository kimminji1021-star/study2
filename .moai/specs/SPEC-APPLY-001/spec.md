## 1. 개요

숨비투어의 두 번째 업무 기능이다. 방문자는 투어 상세에서 회차를 고른 뒤 신청 화면에서 인원과 연락처를 적고 개인정보 수집·이용에 동의해 신청을 낸다. 서버는 정원을 다시 확인해 신청을 저장하고, 정원이 차면 같은 작업 안에서 회차를 마감한다. 방문자는 접수 번호가 적힌 접수 완료 화면을 보고, 관리자는 Payload 관리자 화면에서 신청을 읽기만 한다. 범위는 다음 일곱 가지다.

1. 데이터 모델: `applications`(신청)와 `application-attempts`(신청 시도 기록) 컬렉션, 신청이 있는 회차의 삭제 거부
2. 접근 규칙: 어떤 API로도 신청을 만들거나 바꾸거나 지울 수 없고, 읽기는 관리자만 한다. 생성은 사이트의 서버 쪽 제출 경로 하나뿐이다
3. 점유 인원: 대기·확정 신청 인원의 합계. 정의는 한 곳에만 두고 화면 표시와 신청 처리가 함께 쓴다
4. 정원 처리: 트랜잭션 안에서 회차 행을 잠그고 남은 자리를 다시 확인한 뒤 저장, 정원에 닿으면 자동 마감. 동시 신청에도 정원을 넘지 않는다
5. 화면: 상세의 "신청하기", 신청 화면(입력·동의·안내), 접수 완료 화면(POST 뒤 리다이렉트)
6. 스팸 방지: 허니팟 입력란과 DB에 기록하는 신청 횟수 제한
7. 테스트: 단위·통합(실제 DB 병렬 제출 포함)·E2E와 저장소 규칙 갱신

### 2.2 사용자가 확정한 사항 (2026-11-10 인터뷰, 구속력 있음)

- **D1. 신청 인원**: 1 이상 10 이하의 정수이며, 회차의 남은 자리를 넘을 수 없다.
- **D2. 스팸 방지**: 허니팟 입력란과 간단한 횟수 제한만 쓴다. 외부 서비스·캡차는 쓰지 않는다. 횟수 기록 위치는 초안 작성자가 정한다(`plan.md` §B.5).
- **D3. 접수 완료**: 별도 페이지에 접수 번호·투어·회차·인원·"대기 — 관리자 확인 후 확정"을 보여 주고 개인정보는 보여 주지 않는다. 새로고침해도 다시 제출되지 않는다. 접수 번호는 추측·열거할 수 없고 DB 순번 ID를 드러내지 않는다.
- **D4. 관리자 범위**: 관리자 화면에서 읽기만 한다. 상태 변경과 취소 복원 규칙은 로드맵 6번. 새 신청의 기본 상태는 대기다.

Tier는 M으로 정한다. 신청 접수라는 단일 도메인이고 프로젝트 원칙을 바꾸지 않는다. 직접 작성할 제품 코드는 약 1,000줄, 테스트는 그보다 조금 많을 것으로 보여 Tier M 지침(5~15개 파일, 1,000줄)을 넘을 수 있다. SPEC-TOUR-001도 같은 이유로 Tier M을 유지했다. 요구사항 16개·수용 기준 16개로 Tier M 예산 안이며, 분할 기준은 `plan.md` §A.3에 둔다.

### 2.3 이 SPEC이 내리는 결정 (요약 — 근거는 `plan.md` §B)

- **동시성 제어**: 명시적 트랜잭션 안에서 회차 행을 `SELECT … FOR UPDATE`로 잠근 뒤, 별도 문장으로 점유 인원 합계를 다시 읽어 판단한다. 잠금 대기는 5초로 제한한다. 로컬 PostgreSQL 17에서 잠금이 있으면 뒤 트랜잭션이 앞 트랜잭션의 저장을 보고 거절하고, 잠금이 없으면 정원을 넘는 것을 실측했다(`plan.md` §A.2).
- **점유 인원은 저장하지 않는다**: 매번 합계로 구한다. 목록·상세는 회차 묶음당 질의 1회로 모아 센다.
- **생성 경로는 서버 액션 하나**: `applications`의 생성·수정·삭제 접근 규칙은 관리자를 포함한 모두에게 거부다. 서버 액션은 로컬 API를 접근 규칙 없이(`overrideAccess: true`) 호출하는 유일한 경로다.
- **접수 번호**: `SB-` + Crockford Base32 10자(50비트 난수, `SB-XXXXX-XXXXX`). 고유 제약을 둔다.
- **횟수 제한 기록은 DB**: 메모리는 서버리스 인스턴스마다 따로 있고 재시작에 사라지므로 쓰지 않는다. IP는 키 해시(HMAC-SHA256)로만 저장한다.
- **새 npm 패키지 없음**: 해시·난수는 Node 내장 `node:crypto`, SQL 태그는 이미 직접 의존성인 `@payloadcms/db-postgres`가 내보내는 `sql`을 쓴다.

### 2.4 기록된 가정

- **A1. 관리자 판정**: SPEC-TOUR-001 가정 A1과 같다(`users` 컬렉션 사용자).
- **A2. 상태를 바꾸는 경로가 없다**: 이 SPEC에서 신청 상태는 생성 시의 대기뿐이다. 관리자 화면은 읽기 전용이고 상태 변경은 로드맵 6번이다. 따라서 "마감 전 취소는 정원에서 뺀다"는 규칙은 점유 인원 정의(취소 제외)로만 구현하고, 취소로 마감이 풀리는 경로는 만들지 않는다.
- **A3. 입력값을 다시 채우는 것은 노출이 아니다**: 검증 오류 뒤 신청 화면이 방문자 본인의 입력값을 입력란에 다시 채우는 것은 허용한다. 오류 문구·오류 코드·로그·URL·접수 완료 화면에는 개인정보를 넣지 않는다.
- **A4. 영문 동의 문구는 다국어 SPEC으로 미룬다**: `product.md` §8.3은 국문·영문 고지를 요구하지만 이 SPEC은 한국어만 다룬다(로드맵 7번). 사이트가 영문 화면을 열기 전까지 영문 고지가 없어도 고지 대상과 언어가 어긋나지 않는다.
- **A5. 접속 IP의 출처**: `x-forwarded-for`의 첫 값을 쓴다. Vercel은 이 머리글을 덮어써 위조를 막는다고 공식 문서에 적혀 있다(`plan.md` §B.5). 로컬 개발 서버에서는 위조할 수 있으며 이는 받아들인다.
- **A6. 보관 기준일**: 신청 기록의 보관 기준일은 "취소일이 있으면 취소일, 없으면 회차 종료 일시"다. 이 SPEC은 취소일 필드를 비워 두고 회차 종료 일시는 회차 관계로 구한다. 이를 위해 신청이 있는 회차는 삭제할 수 없다(A7). 실제 파기 작업은 범위 밖이다.
- **A7. 신청이 있는 회차는 삭제하지 않음**: 회차를 지우면 신청의 보관 기준일과 정원 기록이 사라진다. SPEC-TOUR-001 가정 A3(회차가 있는 투어 삭제 거부)과 같은 원칙이다.
- **A8. 접수 완료 화면은 접수 번호만 알면 열린다**: 개인정보가 없고 접수 번호는 추측할 수 없으므로 별도 인증을 두지 않는다.
- **A9. 법률 문구는 초안이다**: 동의 문구와 보유기간 표현은 `product.md` §8.3의 참고안이며 **출시 전 전문가 확인 필요**다.

### 2.5 용어

- **신청**: `applications` 문서 하나. 회차·이름·이메일·연락처·인원·요청 사항(선택)·상태·동의 기록·접수 번호를 가진다.
- **상태**: 대기(`pending`) / 확정(`confirmed`) / 취소(`cancelled`). 새 신청은 대기다.
- **점유 인원**: 한 회차에 속한 대기·확정 신청 인원의 합계. 취소 신청은 세지 않는다.
- **남은 자리**: SPEC-TOUR-001 정의 그대로(정원 − 점유 인원, 0 미만이면 0). 이 SPEC부터 점유 인원이 실제 값이다.
- **신청 가능 회차**: SPEC-TOUR-001의 "선택 가능한 회차"(모집 중 ∧ 시작 시각 > 현재 ∧ 남은 자리 ≥ 1)이면서 공개 투어에 속한 회차.
- **서버 제출 경로**: 신청 화면의 양식이 보내는 서버 액션과 그것이 부르는 `src/lib/`의 신청 처리 함수. 신청을 만드는 유일한 경로다.
- **정원 확인 구간**: 서버 제출 경로 안에서 회차 행 잠금부터 커밋 또는 롤백까지의 트랜잭션 구간.
- **접수 번호**: 신청마다 무작위로 만든 공개 식별자. DB의 순번 ID와 관계없다.
- **신청 시도 기록**: 횟수 제한을 위해 서버 제출 경로가 시도마다 남기는 `application-attempts` 문서. 접속 IP의 키 해시와 시도 시각만 담는다.
- **개인정보**: 이 SPEC에서 신청자의 이름·이메일·연락처·요청 사항을 말한다.
- **동의 문구 버전**: 필수·선택 동의 문구 묶음의 식별 문자열. 문구가 바뀌면 버전도 바뀐다.
- **오류 코드**: 서버 제출 경로가 돌려주는 영문 대문자 코드. 목록은 `acceptance.md` §0.
- **테스트 데이터 표식**: SPEC-TOUR-001과 같다. 신청은 이름에 표식을, 이메일은 `@example.test`로 끝나는 값을 쓴다.

## 3. 요구사항 (GEARS)

패턴 표기: [Ubiquitous] 상시 / [Event-driven] **When** / [State-driven] **While** / [Unwanted] 금지. Tier M 예산(요구사항 16개 이하)에 맞춰 관련 조항을 묶었다.

### 3.1 데이터 모델

- **REQ-APPLY-001** [Ubiquitous + Event-driven] Payload 설정은 신청 컬렉션 `applications`를 등록해야 한다. 신청은 회차(필수, `tour-sessions` 참조), 이름, 이메일, 연락처, 인원, 요청 사항(선택), 상태(대기·확정·취소, 기본값 대기), 접수 번호(모든 신청에서 고유), 필수 동의 일시, 동의 문구 버전, 요청 사항 선택 동의 일시(선택), 취소일(선택, 이 SPEC에서는 비어 있음)을 가져야 한다. 인원은 1 이상 10 이하의 정수, 요청 사항은 500자 이하여야 한다. **When** 이 규칙에 맞지 않는 값이나 비어 있는 필수 값이 저장 요청에 들어오면, 저장은 검증 오류로 끝나고 문서를 만들거나 바꾸지 않아야 한다.
- **REQ-APPLY-002** [Ubiquitous] Payload 설정에 등록된 컬렉션 중 시스템 컬렉션(slug가 `payload-`로 시작)을 뺀 목록은 정확히 `users`, `media`, `tours`, `tour-sessions`, `applications`, `application-attempts`여야 한다. 이 요구사항은 SPEC-TOUR-001 REQ-TOUR-004의 목록을 대체한다.

### 3.2 접근 규칙과 데이터 무결성

- **REQ-APPLY-003** [Unwanted + State-driven] `applications`와 `application-attempts`의 생성·수정·삭제는 접근 규칙을 적용하는 모든 경로(REST, GraphQL, `overrideAccess: false`인 로컬 API, 관리자 화면)에서 익명 방문자와 관리자 모두에게 거부되어야 하며, 거부된 요청은 데이터를 바꾸지 않아야 한다. `application-attempts`는 누구도 읽을 수 없어야 하고 관리자 화면 메뉴에 나타나지 않아야 한다. **While** 요청이 관리자의 것이 아니면, `applications` 읽기 결과는 비어 있거나 권한 오류여야 한다. 관리자는 관리자 화면에서 신청 목록과 상세를 읽을 수 있어야 한다. 신청은 서버 제출 경로로만 만들어져야 한다.
- **REQ-APPLY-004** [Event-driven + Unwanted] **When** 신청이 하나 이상 연결된 회차의 삭제가 요청되면, 시스템은 회차와 신청을 삭제하지 않고 영문 고정 문구(`acceptance.md` AC-APPLY-004)를 담은 오류로 끝나야 한다. 관리자도 예외가 아니다.

### 3.3 점유 인원과 표시

- **REQ-APPLY-005** [Ubiquitous] 회차의 점유 인원은 그 회차에 속한 대기·확정 신청 인원의 합계여야 하며 취소 신청은 세지 않아야 한다. 이 정의는 한 곳에만 있어야 하고, 투어 목록·투어 상세·신청 화면의 남은 자리 표시와 서버 제출 경로의 정원 판단이 모두 이 정의를 써야 한다. 화면의 남은 자리와 신청 가능 여부는 SPEC-TOUR-001의 단일 계산 지점에 이 점유 인원을 넘겨 구해야 한다. 목록·상세 조회 한 번이 데이터베이스에 보내는 질의 수는 회차 수에 따라 늘지 않아야 한다.

### 3.4 화면과 흐름

- **REQ-APPLY-006** [Event-driven + State-driven] **While** 투어 상세에 신청 가능 회차가 하나 이상 있으면, 프론트엔드는 회차 선택 항목과 함께 "신청하기" 버튼을 보여야 한다. **When** 방문자가 신청 가능 회차를 고르고 "신청하기"를 누르면, 프론트엔드는 그 회차의 신청 화면으로 이동해야 한다. 회차를 고르지 않으면 이동하지 않아야 한다. 신청 가능 회차가 없으면 "신청하기"를 보이지 않아야 한다.
- **REQ-APPLY-007** [Event-driven] **When** 방문자가 신청 가능 회차의 신청 화면을 요청하면, 프론트엔드는 투어 제목, 회차 일시, 남은 자리, 신청 입력란(이름·이메일·연락처·인원·요청 사항), 필수 동의 고지와 체크 상자, 요청 사항 선택 동의 고지와 체크 상자, 민감정보 안내 문구, 화면에 보이지 않는 허니팟 입력란을 보여야 한다. 인원 선택지는 1부터 10과 남은 자리 중 작은 값까지여야 한다. **When** 회차 식별 값이 없거나 1 이상 2147483647 이하의 정수가 아니거나, 회차가 없거나 공개 투어에 속하지 않으면, 프론트엔드는 HTTP 404로 응답해야 한다. **When** 회차가 공개 투어에 속하지만 신청 가능 회차가 아니면(마감·시작·자리 없음), 프론트엔드는 신청할 수 없다는 안내와 투어 상세 링크를 보이고 입력 양식을 보이지 않아야 한다.
- **REQ-APPLY-008** [Event-driven + Unwanted] **When** 서버 제출 경로가 신청을 받으면, 서버는 브라우저 쪽 검사와 관계없이 입력을 다시 검증해야 한다. 회차 식별 값은 1 이상 2147483647 이하의 정수, 이름은 앞뒤 공백을 제거한 뒤 1~50자이면서 제어 문자를 포함하지 않아야 하고, 이메일은 Payload 이메일 필드가 받는 형식이면서 254자 이하, 연락처는 원문(앞뒤 공백 제거)이 30자 이하이면서 공백·하이픈·괄호·점을 뺀 값이 `+`(선택) 다음 숫자 8~15자리, 인원은 1~10의 정수, 요청 사항은 500자 이하여야 하고, 필수 동의가 체크되어 있어야 한다. 요청 사항이 비어 있지 않으면 요청 사항 선택 동의가 체크되어 있어야 한다. **When** 하나라도 어긋나면, 서버는 신청을 저장하지 않고 입력란별 영문 오류 코드를 돌려주어야 하며, 화면은 그 코드에 맞는 한국어 안내를 해당 입력란 옆에 보여야 한다. 선택 동의 없이 요청 사항만 버리고 저장하지 않아야 한다.
- **REQ-APPLY-009** [Event-driven + Unwanted] **When** 검증을 통과한 신청이 들어오면, 서버는 하나의 트랜잭션 안에서 회차 행을 잠그고, 그 회차가 공개 투어에 속하고 모집 중이며 시작 전인지와 신청 인원이 남은 자리 이하인지를 잠근 뒤의 데이터로 다시 확인해야 한다. 확인을 통과하면 신청을 대기 상태로 저장하고, 저장 후 점유 인원이 정원과 같아지면 같은 트랜잭션 안에서 회차 상태를 마감으로 바꾼 뒤 커밋해야 한다. **When** 확인에 실패하거나 처리 중 오류가 나면, 서버는 트랜잭션을 되돌려 신청과 회차를 모두 바뀌지 않은 상태로 두고 해당 오류 코드(공개 투어의 회차가 아님·마감·시작함·자리 부족·내부 오류)를 돌려주어야 한다.
- **REQ-APPLY-010** [Ubiquitous + Unwanted + State-driven] 같은 회차에 신청이 동시에 몇 건 들어오더라도, 커밋된 점유 인원은 정원을 넘지 않아야 하고, 받아들인 신청 수는 저장된 신청 수와 같아야 한다. 정원 확인 구간은 회차마다 한 번에 하나씩만 진행되어야 한다. **When** 회차 행 잠금을 5초 안에 얻지 못하면, 서버는 신청을 저장하지 않고 다시 시도하라는 오류 코드를 돌려주어야 한다. **While** 회차가 마감 상태이면, 서버는 그 회차의 신청을 받지 않아야 하며, 시스템은 마감된 회차를 스스로 다시 열지 않아야 한다(신청 상태가 취소로 바뀌어도 마찬가지다).
- **REQ-APPLY-011** [Ubiquitous] 서버는 신청마다 `SB-` 뒤에 Crockford Base32 문자 10자(5자씩 하이픈으로 나눔)로 된 접수 번호를 암호학적 난수로 만들어야 한다. 접수 번호는 모든 신청에서 고유해야 하고, DB 순번 ID와 무관해야 한다. 신청의 DB 순번 ID는 사용자 화면의 URL과 내용에 나타나지 않아야 한다.
- **REQ-APPLY-012** [Event-driven] **When** 신청이 커밋되면, 서버는 접수 완료 화면(`/apply/complete/<접수 번호>`)으로 리다이렉트해야 한다. 자바스크립트 없이 양식을 제출한 경우 이 응답은 HTTP 303이어야 한다. 접수 완료 화면은 접수 번호, 투어 제목, 회차 일시, 인원, 상태 문구(대기는 "대기 — 관리자 확인 후 확정")를 보여야 하고 개인정보를 담지 않아야 하며 검색 엔진 색인을 막아야 한다. 접수 완료 화면을 새로고침하거나 다시 열어도 신청이 새로 만들어지지 않아야 한다. 접수 완료 경로의 접수 번호는 대소문자를 구분하지 않고 받아 대문자로 맞춘 뒤 형식을 검사하고 조회해야 한다. **When** 대문자로 맞춘 뒤에도 형식에 맞지 않거나 없는 접수 번호로 요청하면, 프론트엔드는 HTTP 404로 응답해야 한다.

### 3.5 스팸 방지, 동의, 개인정보

- **REQ-APPLY-013** [Event-driven + Ubiquitous] 서버 제출 경로는 신청 시도마다 접속 IP의 키 해시와 시도 시각을 신청 시도 기록으로 남겨야 하며, 원래 IP 문자열을 저장하지 않아야 한다. **When** 같은 키 해시의 시도가 최근 10분 안에 10회를 넘으면, 서버는 그 시도를 처리하지 않고 횟수 제한 오류 코드를 돌려주어야 한다. **When** 허니팟 입력란에 값이 있으면, 서버는 신청을 저장하지 않고 이유를 드러내지 않는 일반 거부 오류 코드를 돌려주어야 한다. 시도 시각이 10분보다 오래된 신청 시도 기록은 다음 신청 시도를 처리할 때 지워져야 한다.
- **REQ-APPLY-014** [Ubiquitous + Event-driven] 신청 화면의 필수 동의 고지는 ① 수집 항목 ② 이용 목적 ③ 보유기간(투어 종료일, 취소한 경우 취소일부터 5년) ④ 동의를 거부할 권리와 거부하면 신청할 수 없다는 사실을 담아야 하고, 요청 사항 선택 동의 고지는 수집 항목·목적·보유기간(투어 종료 후 지체 없이 파기)·거부해도 신청할 수 있다는 사실을 담아야 하며, 요청 사항 입력란 가까이에 "건강·장애 등 민감한 정보는 적지 마세요" 안내가 있어야 한다. **When** 신청이 저장되면, 서버는 필수 동의 일시와 동의 문구 버전을 기록하고, 요청 사항 선택 동의가 있고 요청 사항이 비어 있지 않으면 그 일시도 기록해야 한다. 두 동의 일시는 서버 제출 경로가 그 신청을 처리한 시각(신청 시도 기록과 같은 현재 시각)이어야 한다. 동의 문구가 바뀌면 동의 문구 버전도 바뀌어야 한다.
- **REQ-APPLY-015** [Unwanted] 서버 제출 경로와 신청 관련 화면은 개인정보를 서버 로그, 오류 코드, 오류 문구, URL(경로와 질의 문자열), 접수 완료 화면에 담지 않아야 한다. 서버 제출 경로가 기록하는 로그는 오류 코드, 오류 종류 이름(예: `ValidationError`), 회차 식별 값만 담아야 하며, 잡은 오류의 메시지 원문을 기록하거나 돌려주지 않아야 한다.

### 3.6 테스트

- **REQ-APPLY-016** [Ubiquitous] 테스트 실행(`pnpm test`, `pnpm e2e`)은 이 SPEC의 순수 함수(단위), 컬렉션 검증·접근 규칙·점유 인원·서버 제출 경로·횟수 제한(통합, 실제 PostgreSQL), 그리고 실제 PostgreSQL에 같은 회차로 병렬 제출해 정원을 넘지 않음을 확인하는 동시성 테스트(통합), 신청 화면 흐름·접수 완료·404·권한(E2E)을 검증해야 한다. 테스트는 필요한 데이터를 테스트 데이터 표식을 붙여 스스로 만들고 끝나면 지워야 한다. `src/lib/` 합산 라인 커버리지 85% 기준과 기존 품질 게이트(타입·빌드·린트·포맷·잠금 파일 불변)는 계속 통과해야 한다.

## 4. 비기능 제약

- **보안**: 서버 액션은 신뢰할 수 없는 진입점으로 다룬다(Next 16 문서 `server-actions.md` §Security). 모든 입력을 서버에서 검증하고, 서버 액션의 반환값은 화면에 필요한 값(오류 코드, 다시 채울 입력값)으로 제한한다. 공개되지 않은 투어의 회차에 대한 조작된 제출도 거부한다(REQ-APPLY-009).
- **개인정보**: 수집은 REQ-APPLY-001의 항목으로 한정한다(최소 수집). 요청 사항은 선택 동의가 있을 때만 저장한다. 접속 IP는 키 해시로만, 10분 판단에 필요한 만큼만 둔다. 법률 문구는 출시 전 전문가 확인 필요(가정 A9).
- **동시성**: 데이터베이스 기본 격리 수준(Read Committed)을 바꾸지 않는다. 정원 확인 구간 안의 모든 질의는 같은 트랜잭션 연결을 써야 한다(연결 풀 고갈 방지, `plan.md` §B.1).
- **접근성**: 입력란마다 라벨을 두고, 오류 안내는 해당 입력란과 연결한다. 허니팟은 스크린 리더와 키보드 이동에서 빠져야 한다. 버튼·체크 상자의 터치 영역은 44×44px 이상이다.
- **다국어 대비**: 화면 문구와 동의 문구는 경로 파일 밖의 한 모듈에 모아 로드맵 7번에서 언어별로 나눌 수 있게 한다.
- **Windows 호환**: 새 스크립트·검증 명령은 PowerShell 5.1에서 동작해야 한다.
- **비용**: 새 유료 서비스·외부 저장소·새 npm 패키지를 쓰지 않는다.

수용 기준과 검증 명령은 `acceptance.md`에 둔다.

## 5. 제외 범위 (Out of Scope)

### Out of Scope — 관리자 운영 기능 (로드맵 6번)

- 신청 상태 변경(대기·확정·취소 전환)과 취소 → 대기·확정 복원 시 정원 확인
- 관리자가 마감된 회차를 다시 여는 화면·규칙의 추가 작업(기존 회차 상태 필드 수정은 그대로 둔다)
- 회차 정원을 점유 인원보다 작게 바꾸는 경우의 처리
- CSV 내려받기, 통계 대시보드, 관리자 화면 커스터마이징

### Out of Scope — 회원과 알림

### Out of Scope — 다국어와 결제

- 영문 화면과 영문 동의 문구, 신청 언어 필드(로드맵 7번)
- 온라인 결제·환불(`product.md` §6)

### Out of Scope — 개인정보 파기 작업

- 보유기간이 지난 신청의 분리 보관·파기, 투어 종료 후 요청 사항 파기 작업

- 신청 시도 기록의 예약 정리 작업(배포 SPEC — 이 SPEC은 다음 시도 때 지운다)
- 개인정보 처리방침 문서 작성과 링크 연결

### Out of Scope — 스팸 방지 고도화와 배포

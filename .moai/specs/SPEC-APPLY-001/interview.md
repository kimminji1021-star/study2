# SPEC-APPLY-001 인터뷰 기록

> 대상: 로드맵 3번 "신청 흐름 + 정원" (`.moai/project/product.md` §7)
> 진행: 2026-11-10, 오케스트레이터가 사용자와 진행했다. 아래 질문 문구는 오케스트레이터 위임 지시에 남은 결정 내용을 바탕으로 다시 적은 요약이며, 답은 결정 내용 그대로다.
> 효력: 아래 4가지 결정은 이 SPEC을 구속한다. 초안 작성 중 다시 묻지 않는다.

## Q1. 한 번 신청할 때 인원은 몇 명까지 받을까요?

- **답**: 1명 이상 10명 이하의 정수. 그리고 해당 회차의 남은 자리보다 많을 수 없다.
- 반영: REQ-APPLY-001(필드 규칙), REQ-APPLY-008(입력 검증), REQ-APPLY-009(남은 자리 재확인)

## Q2. 스팸은 어느 수준까지 막을까요?

- **답**: 기본 수준만. 숨긴 입력란(허니팟) 하나와 간단한 신청 횟수 제한. 외부 서비스나 캡차는 지금 쓰지 않는다.
- 위임된 판단: 횟수 제한 기록을 어디에 둘지는 초안 작성자가 근거와 함께 정한다. 서버리스(Vercel) 환경에서는 메모리 보관이 믿을 수 없다는 점을 고려하고, 배포 SPEC이 다시 확인할 항목을 적는다.
- 반영: REQ-APPLY-013, `plan.md` §B.5

## Q3. 신청을 마친 뒤 무엇을 보여 줄까요?

- **답**: 별도 접수 완료 페이지.
  - 접수 번호, 투어·회차·인원, 상태 "대기 — 관리자 확인 후 확정"을 보여 준다.
  - 개인정보(이름·이메일·연락처·요청 사항)는 보여 주지 않는다.
  - 새로고침해도 다시 제출되지 않아야 한다(POST 뒤 리다이렉트 후 GET 또는 같은 효과).
  - 접수 번호는 추측하거나 차례로 훑어볼 수 없어야 한다. 데이터베이스의 순번 ID를 드러내지 않는다.
- 반영: REQ-APPLY-011, REQ-APPLY-012, REQ-APPLY-015

## Q4. 관리자는 이번 SPEC에서 신청을 어디까지 다룰까요?

- **답**: Payload 관리자 화면에서 **보기만** 한다(읽기 전용).
  - 상태 변경(대기·확정·취소 전환)과 취소 복원 시 정원 확인 규칙은 로드맵 6번에서 다룬다.
  - 새 신청의 기본 상태는 대기(pending)다.
- 반영: REQ-APPLY-001(기본 상태), REQ-APPLY-003(접근 규칙)

## 이미 정해진 제품 규칙 (위임 지시에 명시 — 이 SPEC이 그대로 담는다)

- 비회원 신청만(회원은 로드맵 4번), 이메일 없음(로드맵 5번), 한국어만(로드맵 7번)
- 정원은 대기·확정 신청 인원의 합계로 차감하고, 마감 전에는 취소 신청을 세지 않는다
- 합계가 정원에 닿으면 같은 원자적 작업 안에서 회차를 자동으로 마감한다. 한번 마감된 회차는 자동으로 다시 열지 않는다(관리자 수동 — 로드맵 6번)
- 동시에 제출해도 정원을 넘지 않는다. 실제 DB에 병렬로 제출하는 테스트로 증명한다
- 동의 화면: 필수 동의(① 수집 항목 ② 목적 ③ 보유기간 ④ 거부할 권리와 거부 시 신청 불가), 요청 사항은 별도 선택 동의, 민감정보 안내 문구, 동의 일시·문구 버전·보관 기준일 기록. 법률 문구는 "출시 전 전문가 확인 필요"
- 익명 사용자는 REST·GraphQL·로컬 API로 신청을 읽거나 바꾸거나 지울 수 없다. 생성은 사이트의 서버 쪽 제출 경로로만. 관리자는 읽기만. 개인정보를 로그나 오류에 남기지 않는다
- 목록·상세의 남은 자리는 점유 인원을 뺀 값으로 보여 준다(단일 계산 지점 확장, 회차마다 조회하지 않음)
- 서버 쪽 검증이 기준이다. 오류 코드·메시지는 영문(`error_messages: en`), 화면 문구는 한국어

# SPEC-APPLY-001 수용 기준

> **검증 셸**: Windows PowerShell 5.1에서 그대로 실행되어야 한다(PowerShell 7 확인은 SPEC-INFRA-001의 수용한 부채를 따른다). 명령 인자 안에 큰따옴표를 겹쳐 쓰지 않는다. 문자열·구조 검사는 셸 인용에 기대지 않고 테스트 코드(저장소 규칙 테스트 `tests/unit/repo-rules.spec.ts` 포함)나 `Select-String -SimpleMatch '<고정 문자열>'`로 한다.
> **판정**: 별도 표시가 없으면 "통과"는 해당 명령의 종료 코드가 0(`$LASTEXITCODE -eq 0`)임을 뜻한다.
> **빈 결과 방지**: "0건"이나 "없음"을 검사하는 테스트는 같은 검사 안에서 대상이 1건 이상 존재함(또는 검사가 실제로 무언가를 수집했음)을 먼저 단언한다.
> **전제**: SPEC-INFRA-001·SPEC-TOUR-001의 전제와 같다(`.env` 존재, PostgreSQL 컨테이너 `healthy`). `pnpm test`, `pnpm e2e`로 판정하는 기준은 모두 이 상태를 전제로 한다.
> **테스트 데이터 표식**: SPEC-TOUR-001과 같다(투어 slug·제목 `test-<무작위 값>…`, 관리자 이메일 `@example.test`). 신청은 이름에 표식을 넣고 이메일은 `<표식>@example.test`로 쓴다. 접속 IP는 문서용 주소 대역(`203.0.113.0/24`, `198.51.100.0/24`)만 쓴다. 테스트는 시드 데이터나 개발자가 만든 데이터에 기대지 않는다.
> **시각 기준**: 신청 가능 회차는 실행 시각 기준 하루 이상 뒤에 시작한다. "시작함" 사례만 하루 전에 시작한 회차를 쓴다. 횟수 제한의 시간 창은 신청 처리 함수에 현재 시각을 주입해 검증한다.
> **신청 처리 함수**: 통합 테스트는 서버 액션이 부르는 `src/lib/`의 신청 처리 함수를 Next 없이 직접 호출한다(이름은 run 단계가 정한다). 이 문서에서 "제출한다"는 이 함수 호출 또는 E2E의 양식 제출을 뜻한다.
> **테스트 데이터 독립**: 각 수용 기준의 투어·회차·신청 데이터는 그 기준 전용으로 만든다. 이름이 같아도("투어 T, 회차 A") 다른 기준과 공유하지 않는다.

## 1. 데이터 모델과 접근 규칙

### AC-APPLY-001 — 등록 컬렉션

- **Given** 소스가 준비되어 있다
- **When** `pnpm test`를 실행한다
- **Then** 통합 테스트가 Payload 설정의 컬렉션 slug 목록에서 `payload-`로 시작하는 slug를 뺀 결과(정렬 후)가 정확히 `['application-attempts', 'applications', 'media', 'tour-sessions', 'tours', 'users']`임을 단언하고 통과한다
- **And** 같은 테스트는 필터 전 목록이 필터 후보다 길다는 것을 먼저 단언한다
- **And** 기존 `Users` 인증 흐름 테스트(생성·로그인·틀린 비밀번호·삭제)가 계속 통과한다

### AC-APPLY-002 — Applications 필드 검증과 입력 규칙 일관성

- **Given** 통합 테스트가 테스트 데이터 표식을 붙인 공개 투어 1개와 회차 1개(정원 50)를 만들고, 모든 필수 값을 갖춘 신청 입력값을 준비한다
- **When** `pnpm test`를 실행한다
- **Then** 통합 테스트가 로컬 API(접근 규칙 생략 — 서버 제출 경로와 같은 권한)로 다음을 확인한다
  - 필수 값을 모두 갖춘 신청은 저장되고, 상태를 지정하지 않으면 `pending`으로 저장된다
  - 인원 `0`, `11`, `1.5`는 검증 오류로 끝나고 문서가 생기지 않으며, `1`과 `10`은 저장된다
  - 요청 사항 501자는 검증 오류, 500자는 저장된다
  - 회차·이름·이메일·연락처·인원·접수 번호·필수 동의 일시·동의 문구 버전 중 하나라도 빠지면 검증 오류로 끝난다(필드별로 1건씩)
  - 이미 쓰인 접수 번호로 두 번째 신청을 만들면 오류로 끝나고 그 접수 번호의 문서가 하나만 남는다
- **And** 단위 테스트와 통합 테스트가 같은 이메일 표본으로 다음을 확인한다: 서버 입력 검증 함수가 받는 표본(`<표식>@example.test`, `kim.minji+<표식>@example.test`, `user-name-<표식>@sub.example.test`)은 컬렉션 저장도 성공하고, 서버 입력 검증 함수가 거부하는 표본(`a@b`, `a b@example.test`, `"a"@example.test`, `a..b@example.test`, 255자 주소)은 `EMAIL_INVALID`다. 저장하는 표본은 모두 표식을 담고 `example.test`로 끝난다(AC-APPLY-016 정리 확인 대상). 거부 표본은 저장하지 않는다. 받는 표본 3개가 Payload `email` 필드 정규식을 통과함은 계획 단계에서 표식 `test-ab12cd34`로 계산해 확인했다

### AC-APPLY-003 — 쓰기 권한과 읽기 범위 (로컬 API·REST·GraphQL·관리자 화면)

- **Given** 테스트 관리자 계정(`@example.test`)과, 테스트 데이터 표식을 붙인 신청 1건 및 신청 시도 기록 1건이 있다
- **When** `pnpm test`와 `pnpm e2e`를 실행한다
- **Then** 통합 테스트가 로컬 API를 접근 규칙 적용 상태(`overrideAccess: false`)로 호출해 다음을 확인한다
  - 사용자 없음(익명)과 테스트 관리자 사용자 모두에서 `applications`·`application-attempts`의 생성·수정·삭제가 권한 오류로 끝나고, 호출 전후의 문서 수와 값이 같다
  - 익명의 `applications` 조회는 권한 오류이거나 결과 0건이고, 테스트 관리자의 조회 결과에는 준비한 신청이 있다
  - 테스트 관리자를 포함한 누구의 `application-attempts` 조회도 권한 오류이거나 결과 0건이다
- **And** E2E가 Playwright 요청 API로 다음을 확인한다
  - REST 대조군: 테스트 관리자 인증으로 `GET /api/applications?where[email][equals]=<준비한 이메일>`을 보내면 응답 상태가 200이고 `totalDocs`가 1이며 응답 본문에 그 이메일이 있다(대상 존재 단언 — 이메일로 걸러 페이지 크기의 영향을 받지 않음)
  - 같은 요청을 익명으로 보내면 응답 상태가 403이거나, 200이면 `docs`가 빈 배열이다. 어느 쪽이든 응답 본문에 그 이메일이 없다
  - GraphQL 대조군: 테스트 관리자 인증으로 `POST /api/graphql`에 이메일을 질의문에 직접 넣은 `{ Applications(where: { email: { equals: "<준비한 이메일>" } }) { docs { email } } }`(변수 형 선언을 쓰지 않음)를 보내면 응답 상태가 200이고 `errors`가 없으며 `data.Applications.docs`에 그 이메일이 있다
  - 같은 질의를 익명으로 보내면 응답 본문에 그 이메일이 없고, `errors`의 메시지 중 하나가 `You are not allowed to perform this action.`(Payload `Forbidden`)이거나 `data.Applications.docs`가 빈 배열이다
  - 익명과 테스트 관리자 각각의 `POST /api/applications`(표식 이메일을 쓴 본문)의 응답 상태가 정확히 403이고, 이후 그 이메일의 신청이 없다. Payload는 생성 접근 검사를 입력 검증보다 먼저 하므로 본문이 불완전해도 403이 나와야 한다(`plan.md` §A.2)
  - 테스트 관리자의 `PATCH /api/applications/<id>`(상태를 `confirmed`로)와 `DELETE /api/applications/<id>`의 응답 상태가 각각 정확히 403이고, 이후 그 신청이 그대로(상태 `pending`) 있다. 익명의 같은 두 요청도 각각 정확히 403이다
- **And** (수동) 관리자 화면에서 신청 목록과 상세가 열리고, 상세의 입력란이 편집할 수 없으며, "새로 만들기" 버튼과 저장 버튼이 없고, 메뉴에 신청 시도 기록 컬렉션이 없다. 결과를 `progress.md` §E.2에 기록한다

### AC-APPLY-004 — 신청이 있는 회차의 삭제 거부

- **Given** 테스트 데이터 표식을 붙인 투어 1개, 회차 1개, 그 회차의 신청 1건이 있다
- **When** `pnpm test`를 실행한다
- **Then** 통합 테스트가 관리자 권한으로 그 회차 삭제를 요청하면 오류로 끝나고, 오류 메시지에 영문 고정 문자열 `Cannot delete a session that has applications`가 들어 있으며, 회차와 신청이 모두 그대로 있음을 확인한다
- **And** 신청을 먼저 지운 뒤 회차를 삭제하면 성공한다

## 2. 점유 인원과 표시

### AC-APPLY-005 — 점유 인원 정의와 질의 수

- **Given** 통합 테스트가 공개 투어 T와 회차 S1(정원 5)을 만들고, S1에 대기 2명·확정 1명·취소 2명 신청을 로컬 API로 직접 만들었다
- **When** `pnpm test`를 실행한다
- **Then** 통합 테스트가 다음을 확인한다
  - 점유 인원 모듈이 S1에 대해 3을 돌려준다(취소 제외). 신청이 없는 회차는 0이다
  - 조회 계층의 목록용·상세용 결과에서 S1의 남은 자리가 2, 정원이 5다
  - 정원 3인 회차 S2에 대기 3명을 만들면 조회 계층 결과에서 S2의 남은 자리가 0이고 선택 불가 사유가 자리 없음(`full`)이다
- **And** 질의 수 검사: 공개 투어 Q에 예정 회차 1개(신청 1건)만 있는 상태에서 목록 조회 한 번과 Q의 상세 조회 한 번이 실행하는 동안 `payload.db.pool.query` 호출 수를 각각 센다. 이어서 Q에 예정 회차 5개(각 신청 1건)를 더한 뒤 같은 두 조회의 호출 수를 다시 센다. 목록끼리, 상세끼리 두 수가 같고 각각 1 이상이다(투어 집합은 두 측정에서 같고 회차 수만 다르다)
- **And** 같은 네 측정 구간마다 `payload.db.pool.connect` 호출 수도 세어, 각 구간에서 `connect` 호출 수가 `query` 호출 수와 같다(`Pool.query`가 내부에서 `connect`를 한 번씩 부르므로, 차이가 0이면 트랜잭션 등 직접 연결로 나간 질의가 없다는 뜻 — `plan.md` §A.2)

### AC-APPLY-006 — 목록·상세의 남은 자리와 "신청하기"

- **Given** E2E 준비 단계가 AC-APPLY-005와 같은 투어 T(S1 +2일 정원 5에 대기 2·확정 1·취소 2, S2 +3일 정원 3에 대기 3)와, 마감 회차만 있는 공개 투어 U를 만들었다
- **When** `pnpm e2e`를 실행한다
- **Then** E2E 테스트가 다음을 확인한다
  - `/tours`의 T 카드에 "남은 자리 2 / 5"가 보인다
  - `/tours/<T의 slug>`에서 S1 행에 "남은 자리 2 / 5"가, S2 행에 "남은 자리 0 / 3"과 "자리 없음" 배지가 보이고 S2의 선택 항목은 비활성(`disabled`)이다
  - 상세에 "신청하기" 버튼이 있다. 회차를 고르지 않고 누르면 경로가 바뀌지 않는다. S1을 고르고 누르면 경로가 `/apply`이고 질의 문자열 `session`의 값이 S1의 ID다
  - `/tours/<U의 slug>`에는 "신청하기" 버튼이 없다

## 3. 신청 화면과 서버 처리

### AC-APPLY-007 — 신청 화면 구성, 404, 신청 불가 안내

- **Given** E2E 준비 단계가 공개 투어 T의 회차 A(+2일 정원 15, 신청 없음), 회차 B(+2일 정원 5, 모집 중, 대기 신청 2건 각 인원 1 — 점유 인원 2), 마감 회차 C, 시작한 회차 E(하루 전 시작, 모집 중, 정원 15, 신청 없음), 자리 없는 회차 F(+2일 정원 2, 모집 중, 대기 신청 1건 인원 2 — 점유 인원 2), 공개되지 않은 투어 H의 회차 D를 만들었다. B·F의 신청은 준비 단계가 로컬 API로 직접 만들고 이름에 표식, 이메일은 `<표식>-<번호>@example.test`를 쓴다(AC-APPLY-016 정리 대상). F는 상태를 `open`으로 둔 채 점유 인원이 정원과 같은 회차다
- **When** `pnpm e2e`를 실행한다
- **Then** E2E 테스트가 `/apply?session=<A의 ID>`에서 다음을 확인한다
  - 응답이 HTTP 200이고 E2E 포트 단언이 통과한다
  - 투어 제목, 회차 일시 표기, "남은 자리 15 / 15"가 보인다
  - 이름·이메일·연락처·인원·요청 사항 입력란이 각각 라벨과 연결되어 있다
  - 필수 동의 체크 상자와 요청 사항 선택 동의 체크 상자가 따로 있고 둘 다 처음에 체크되어 있지 않다
  - 필수 동의 체크 상자의 `aria-describedby`가 가리키는 요소(필수 고지) 안에 고정 문자열 `수집 항목`, `이용 목적`, `보유 기간`, `5년`, `거부하면 신청할 수 없습니다`가 각각 있다
  - 선택 동의 체크 상자의 `aria-describedby`가 가리키는 요소(선택 고지) 안에 고정 문자열 `투어 종료 후 지체 없이 파기`, `거부해도 신청할 수 있습니다`가 각각 있다

  - 같은 시각에 접속 IP `203.0.113.11`의 제출 → 성공
  - 이 시점(아래 시간 경과 제출 전)에 저장된 신청 시도 기록의 키는 16진수 64자이고, `203.0.113.10`의 기록들은 키가 모두 같고 `203.0.113.11`의 키와는 다르다
  - 같은 시점에 테스트가 `node:crypto`로 계산한 `HMAC-SHA256(process.env.PAYLOAD_SECRET, 'apply-rate-limit:203.0.113.10')`의 16진수(`digest('hex')`, 64자)가 `203.0.113.10`의 저장된 키와 같고, 키 없는 `SHA-256('203.0.113.10')`의 16진수와는 다르다. 키 유도 입력은 `plan.md` §B.5의 정의(`'apply-rate-limit:' + ip`)와 같은 문자열이다. 키 없는 해시는 IPv4 공간 전체를 짧은 시간에 대입해 원래 IP로 되돌릴 수 있으므로 이 단언으로 구분한다. 테스트는 비밀 값을 출력하지 않는다
  - 같은 시점에 로컬 API로 읽은 신청 시도 기록 문서 전체를 `JSON.stringify`한 문자열에 `203.0.113.10`, `203.0.113.11`, `203.0.113.12`가 모두 없다(그 문자열에 기록이 1건 이상 들어 있음을 먼저 단언)
  - 접속 IP `203.0.113.10`, 시각 `now + 10분 + 1초`의 제출 → 성공
  - 그 제출 뒤, 그 시각 기준 10분보다 오래된 신청 시도 기록이 0건이다(시간 경과 제출 직전에 그런 기록이 1건 이상 있었음을 먼저 단언)
- **And** 단위 테스트가 접속 IP 추출 함수에 대해 확인한다: `x-forwarded-for: 198.51.100.7, 10.0.0.1` → `198.51.100.7` / `x-forwarded-for` 없음 + `x-real-ip: 198.51.100.8` → `198.51.100.8` / 둘 다 없음 → `unknown`

### AC-APPLY-014 — 동의 기록과 문구 버전

- **Given** 통합 테스트가 공개 투어의 회차를 준비한다
- **When** `pnpm test`를 실행한다
- **Then** 통합 테스트가 다음을 확인한다
  - 신청 처리 함수에 고정 시각 `now`(실행 시각을 밀리초 단위로 자른 값)를 주입한다
  - 요청 사항 없이 필수 동의만 한 신청: `privacyConsentAt`을 `Date`로 바꾼 값이 `now`와 같은 순간(`getTime()` 일치), `privacyPolicyVersion`이 동의 문구 모듈의 현재 버전 상수, 요청 사항이 비어 있고 `requestsConsentAt`이 비어 있다, `cancelledAt`이 비어 있다
  - 요청 사항과 선택 동의를 함께 한 신청: 요청 사항이 저장되고 `requestsConsentAt`이 `now`와 같은 순간이다
  - 선택 동의만 체크하고 요청 사항은 비운 신청: `requestsConsentAt`이 비어 있다
- **And** 단위 테스트가 다음을 확인한다
  - 동의 문구 모듈의 필수 동의 문구에 `수집 항목`, `이용 목적`, `보유 기간`, `5년`, `거부하면 신청할 수 없습니다`가, 선택 동의 문구에 `거부해도 신청할 수 있습니다`가 있다
  - 동의 문구 버전 상수가 `^\d{4}-\d{2}-\d{2}\.[0-9a-f]{8}$` 형식이다
  - 현재 동의 문구 전체(필수·선택·민감정보 안내를 `plan.md` §B.7의 순서로 이어 붙인 문자열)의 SHA-256 16진수 앞 8자리가 버전 상수의 `.` 뒤 8자리와 같다. 버전 상수는 소스의 문자열 리터럴이므로, 문구를 바꾸고 버전 리터럴을 고치지 않으면 이 단언이 실패한다. 버전 리터럴을 고치면 저장되는 `privacyPolicyVersion`도 바뀐다(보장 범위: 문구 변경 ⇒ 버전 변경)

# SPEC-LANDING-001 인터뷰 기록

> 대상: 로드맵 9번 "랜딩 페이지(디자인)" (`.moai/project/product.md` §7, 2026-11-16 진행 순서의 두 번째)
> 진행: 2026-11-16, 오케스트레이터가 사용자와 진행했다. 아래 질문 문구는 오케스트레이터 위임 지시에 남은 결정 내용을 바탕으로 다시 적은 요약이며, 답은 결정 내용 그대로다.
> 효력: 아래 7가지 결정은 이 SPEC을 구속한다. 초안 작성 중 다시 묻지 않는다.

## Q1. 홈 화면에는 무엇을 둘까요?

- **답**: 두 영역만 둔다.
  - (a) 화면 폭을 가득 채우는 히어로: 대표 사진, 큰 제목, 한 줄 소개, 알약 모양 `투어 둘러보기` 버튼(링크).
  - (b) 추천 투어: 공개 투어를 가장 가까운 예정 회차 순으로 최대 6개. 기존 투어 카드(`TourCard`)를 그대로 쓰고, 남은 자리는 단일 점유 인원 정의로 구하며 회차마다 따로 조회하지 않는다(N+1 없음). 그 아래 `/tours`로 가는 `투어 전체 보기` 링크.
  - 소개(about) 영역과 이용 방법 영역은 두지 않는다.
- 반영: REQ-LANDING-004, REQ-LANDING-007, REQ-LANDING-008

## Q2. 대표 사진은 어떻게 바꿀까요?

- **답**: 운영자가 관리자 화면에서 올린다(예: Payload 전역 설정 "홈 화면 설정"의 `media` 업로드 필드).
  - 사진을 정하기 전에는 깨진 이미지 없이 깔끔한 짙은 면(거의 검은 면)의 히어로를 보인다.
  - 사진을 바꿀 때 코드를 고치지 않는다.
- 반영: REQ-LANDING-001, REQ-LANDING-002, REQ-LANDING-003, REQ-LANDING-005

## Q3. 큰 제목과 소개 문구는 어떻게 할까요?

- **답**: 같은 관리자 설정에서 편집한다. 비어 있으면 적절한 한국어 기본 문구(예: "제주를 가장 가까이, 숨비투어")를 보인다.
- 반영: REQ-LANDING-001, REQ-LANDING-004

## Q4. 머리글에는 무엇을 둘까요?

- **답**: 텍스트 로고 "숨비투어"와 "투어" 링크. 모든 공개 화면(홈, `/tours`, 투어 상세, `/apply`, `/apply/complete`, 404)에 같은 머리글을 둔다. 로그인과 언어 전환은 범위 밖이다(로드맵 4번·7번).
- 반영: REQ-LANDING-009, REQ-LANDING-011

## Q5. 바닥글에는 무엇을 둘까요?

- **답**: 모든 공개 화면에 한 줄짜리 간단한 바닥글: "© 숨비투어"와 "개인정보 처리방침" 자리표시. 처리방침 문서와 사업자·연락처 정보는 배포 단계 항목이다. 자리표시가 어떻게 동작할지는 초안 작성자가 정하고 기록하되, 눌러도 아무 데도 가지 않거나 잘못된 곳으로 가는 링크가 생기지 않게 한다.
- 위임된 판단의 결과: 처리방침 문서가 생기기 전까지 링크가 아닌 글자 `개인정보 처리방침(준비 중)`으로 둔다. `href="#"`나 빈 링크를 만들지 않는다(`plan.md` §B.6).
- 반영: REQ-LANDING-010

## Q6. 디자인은 어떻게 맞출까요?

- **답**:
  - 포인트 색 `#00737A`는 그대로 둔다.
  - 2026-11-16 디자인 방향(`design/handoff.md` §3)을 따른다: 거의 검은 본문 글자, 본문 17px, 좁은 자간의 제목, 알약 버튼, 카드 그림자 없음, 흰 면·연회색 면·짙은 면 번갈아 쓰기, 그림자는 사진에만.
  - 짙은 히어로 위에서 포인트 색 대비가 2.65:1밖에 안 되는 문제를 해결한다(예: 짙은 면 위 흰 알약 버튼). 대비 수치를 기록한다.
  - Pretendard를 제대로 불러온다(지금은 한 번도 불러오지 않는다). `next/font/local`로 직접 호스팅하거나 다른 방법이면 근거를 댄다. 글꼴 라이선스(OFL)를 확인하고 기존 대체 글꼴 목록은 남긴다.
  - 접근성: 랜드마크, 필요하면 본문 바로가기 링크, 대표 사진의 대체 텍스트(관리자 입력 또는 장식용), 동작 줄이기 설정 존중(자동 애니메이션은 필요 없음).
- 위임된 판단의 결과: 공식 배포본 `PretendardVariable.woff2`(v1.3.9)를 바꾸지 않고 저장소에 두어 `next/font/local`로 불러오고 OFL 1.1 전문을 함께 둔다(`plan.md` §B.8). 사진 위에는 균일한 덮개(`rgba(29, 29, 31, 0.65)`)를 깔아 순백 사진에서도 흰 글자 대비 5.24:1을 보장하고, 버튼은 흰 알약에 짙은 글자, 포커스 표시는 흰 외곽선으로 한다(`plan.md` §B.5). 대체 텍스트는 미디어의 필수 대체 텍스트를 쓴다(`plan.md` §B.4).
- 반영: REQ-LANDING-006, REQ-LANDING-012, REQ-LANDING-013, REQ-LANDING-014

## Q7. 이번 SPEC에서 하지 않을 것은?

- **답**: 회원(로드맵 4번), 다국어(7번), 이메일(5번), 배포(8번), 개인정보 처리방침 본문, 사업자 정보, 관리자 화면에서 투어 순서를 정하는 기능, 애니메이션·WebGL, Claude Design 캔버스 갱신.
- 반영: `spec.md` §5

## 이미 정해진 제품 규칙 (기존 SPEC과 프로젝트 문서 — 이 SPEC이 그대로 담는다)

- 점유 인원은 대기·확정 신청 인원의 합계 한 가지로만 구하고(`src/lib/occupancy.ts`, SPEC-APPLY-001 REQ-APPLY-005), 남은 자리는 단일 계산 지점(`getSessionAvailability`, SPEC-TOUR-001 REQ-TOUR-007)만 쓴다
- 사용자 화면의 데이터 조회는 익명 접근 규칙(`overrideAccess: false`)을 우회하지 않는다(SPEC-TOUR-001 REQ-TOUR-005, `src/lib/catalog.ts` 45행)
- 공개 화면은 요청 시점에 렌더링해 관리자가 바꾼 내용이 다시 빌드하지 않아도 반영된다(SPEC-TOUR-001 REQ-TOUR-012)
- 디자인 토큰과 Tailwind 스타일시트는 `(frontend)` 라우트 그룹에서만 불러온다(REQ-INFRA-005, REQ-TOUR-013)
- 상태 배지는 색만으로 구분하지 않는다(`design/handoff.md` §3)
- 화면 문구는 한국어, 오류 문구는 영문(`error_messages: en`)
- 실제 관리자 계정은 건드리지 않는다. 테스트는 `@example.test` 계정과 표식 데이터를 스스로 만들고 지운다
- 새 npm 패키지를 더하지 않는다(SPEC-TOUR-001·SPEC-APPLY-001·SPEC-ADMIN-001과 같은 원칙. 글꼴은 패키지가 아니라 파일로 둔다)
